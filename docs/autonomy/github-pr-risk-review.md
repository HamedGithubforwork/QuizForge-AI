# GitHub PR Risk and Review Evidence

`github-pr-risk-review.cjs` is a read-only evidence collector. It checks the fully paginated PR diff, review decisions, required check runs and their GitHub App issuer, the associated Required PR gate run, the current `main`, effective branch rules, all active listed rulesets, classic branch protection, and a pinned workflow inventory. It takes two complete snapshots and rejects state changes. Its result always contains `mergeAuthorized: false`; it is not connected to the automatic-merge evaluator and cannot approve, authorize, or perform a merge.

## Authentication contract

The collector makes only `GET` requests to `https://api.github.com/repos/HamedGithubforwork/QuizForge-AI/...`. It requires `QUIZFORGE_GITHUB_READ_TOKEN`, captures that value once per inspection, scopes requests to the fixed API host and repository path, rejects redirects, and never returns or logs the token or raw GitHub error body. Missing or malformed credentials, HTTP 401, ordinary HTTP 403, rate limits, network errors, malformed responses, and inconsistent observations all produce `UNVERIFIED`. A 403 rate limit is reported separately from a permission denial using rate-limit headers or a generic rate-limit message; neither is treated as evidence.

An authenticated HTTP 404 is considered absence of classic branch protection only after the same token has successfully read and identity-checked the repository, branch, effective rules, and applicable rulesets. HTTP 401 or 403 is never treated as absence. A successful 200 response for classic protection still blocks this conservative evaluator until the returned settings have an independently reviewed interpretation. The current implementation requires the configured `Protect main` ruleset, matching effective branch rules, and no classic protection.

## Trusted host requirements and limitations

The environment variable is a transport for a credential supplied by a trusted host; it does not authenticate the host or prove that the token is least-privilege. Do not set it in ordinary pull-request CI, expose it to PR-authored code, or persist it in a repository, command line, artifact, log, checkpoint, or workflow output. A production caller must run the reviewed verifier from a trusted revision in a separate trusted process/job that does not execute candidate PR code, and inject a short-lived GitHub App installation token scoped to this repository with read-only permissions only. The required read permissions are Metadata, Contents, Pull requests, Checks, Actions, and Administration (the last is required to inspect classic branch protection/rulesets). No write permission is needed. Do not use a broadly privileged personal `gh` session as the production credential.

The verifier cannot determine whether a process environment was compromised or independently attest which account minted a token. The trusted host must establish token provenance, repository-only installation scope, read-only permission selection, isolation from PR code, and secret handling. Tests use synthetic tokens and mocked API responses; they prove request scoping, pinning, failure handling, and evidence validation only. They do not demonstrate authenticated live verification. At this revision no separately approved, least-privilege installation credential or trusted host runtime is configured, so operational verification remains unavailable and fail-closed. A successful manual `gh api` observation is useful for supervised human review but is not supplied to this module and cannot become automatic-merge evidence.

The collector also does not authenticate Codex specialist invocation records, user approval, or an atomic target/base guard. Even a future trusted live observation from this module would not grant merge authority. Keep `trusted_live_verification_unavailable` and the automatic-merge policy disabled until the separate trusted execution and atomicity requirements are implemented and explicitly authorized.
