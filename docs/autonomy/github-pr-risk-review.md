# GitHub PR Risk and Review Evidence

`github-pr-risk-review.cjs` is a read-only evidence collector. It checks the fully paginated PR diff, review decisions, required check runs and their GitHub App issuer, the associated Required PR gate run, the current `main`, effective branch rules, all active listed rulesets, classic branch protection, and a pinned workflow inventory. It takes two complete snapshots and rejects state changes. GitHub's Actions-run REST object may omit `pull_requests`; in that case the collector verifies the same PR/head/base association through the authenticated, paginated commit-to-PR endpoint. A populated run-level association must agree. Its result always contains `mergeAuthorized: false`; it is not connected to the automatic-merge evaluator and cannot approve, authorize, or perform a merge.

`run-trusted-github-verifier.cjs` is the read-only entry point for `.github/workflows/trusted-github-pr-verification.yml`. The workflow is triggered by completion of the existing `CI` workflow, but the privileged job runs only for the exact CI workflow ID, path, successful `pull_request` event, and repository ID. `workflow_run` executes the workflow definition from the default branch. The job checks out only that default-branch SHA, verifies the checkout/ref/event context, reads only the event's run ID, and then independently re-fetches the run and all PR evidence through the fixed GitHub API client. It never checks out the PR head, runs PR code, consumes artifacts or caches, or grants merge authority. The token is supplied only to the trusted verifier process and is not written to logs, outputs, artifacts, or summaries. The job has no write permission and is not a required PR check.

## Authentication contract

The collector makes only `GET` requests to `https://api.github.com/repos/HamedGithubforwork/QuizForge-AI/...`. It requires `QUIZFORGE_GITHUB_READ_TOKEN`, captures that value once per inspection, scopes requests to the fixed API host and repository path, rejects redirects, and never returns or logs the token or raw GitHub error body. Missing or malformed credentials, HTTP 401, ordinary HTTP 403, rate limits, network errors, malformed responses, and inconsistent observations all produce `UNVERIFIED`. A 403 rate limit is reported separately from a permission denial using rate-limit headers or a generic rate-limit message; neither is treated as evidence.

An authenticated HTTP 404 is considered absence of classic branch protection only after the same token has successfully read and identity-checked the repository, branch, effective rules, and applicable rulesets. HTTP 401 or 403 is never treated as absence. A successful 200 response for classic protection still blocks this conservative evaluator until the returned settings have an independently reviewed interpretation. The current implementation requires the configured `Protect main` ruleset, matching effective branch rules, and no classic protection.

## Trusted host requirements and limitations

The environment variable is a transport for a credential supplied by a trusted host; it does not authenticate the host or prove that the token is least-privilege. Do not set it in ordinary pull-request CI, expose it to PR-authored code, or persist it in a repository, command line, artifact, log, checkpoint, or workflow output. The workflow is prepared to mint a short-lived GitHub App installation token from repository variable `QUIZFORGE_VERIFIER_APP_CLIENT_ID` and secret `QUIZFORGE_VERIFIER_APP_PRIVATE_KEY`, scoped to `HamedGithubforwork/QuizForge-AI`. The variable must contain the GitHub App **Client ID** (not its numeric App ID). The pinned token-minting action alone receives the private-key secret; shell steps do not. If the Client ID is missing, minting is skipped; if the private key is missing or invalid, minting fails safely and inspection reports `UNVERIFIED`. The requested App permissions are Actions:read, Administration:read, Checks:read, Contents:read, and Pull requests:read; all write permissions remain absent. Metadata is available to the installation token. No App, variable, or secret was created or configured as part of this change. Until the owner separately authorizes and configures the narrowly scoped App installation, the workflow reports `UNVERIFIED` and fails its own auxiliary run; it does not affect the Required PR gate. Do not use a broadly privileged personal `gh` session as the production credential.

The verifier cannot determine whether a process environment was compromised or independently attest which account minted a token. The trusted host must establish token provenance, repository-only installation scope, read-only permission selection, isolation from PR code, and secret handling. The workflow uses immutable action commit references, does not persist the checkout credential, and uses the App-token action's default end-of-job revocation. Tests use synthetic tokens and mocked API responses; they prove request scoping, pinning, failure handling, and evidence validation only. They do not demonstrate authenticated live verification. At this revision no separately approved, least-privilege installation credential or trusted App installation is configured, so operational verification remains unavailable and fail-closed. A successful manual `gh api` observation is useful for supervised human review but is not supplied to this module and cannot become automatic-merge evidence.

The collector also does not authenticate Codex specialist invocation records, user approval, or an atomic target/base guard. Even a future trusted live observation from this module would not grant merge authority. Keep `trusted_live_verification_unavailable` and the automatic-merge policy disabled until the separate trusted execution and atomicity requirements are implemented and explicitly authorized.
