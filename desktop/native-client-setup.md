# Dedicated desktop Cognito client — preparation only

The desktop system-browser flow needs its own public client in the **existing Canadian user pool**. No client has been created by these helpers. They neither contact AWS nor change identity settings. Native login is still disabled; registration alone does not enable it.

## Reviewed client policy

- Authorization code grant only, with S256 PKCE generated by the desktop transaction. No client secret, implicit grant, client-credentials grant or direct password authentication.
- Exact callback: `com.quizfromnotes.desktop.preview:/oauth/callback`. Logout returns to `https://quizfromnotes.com/`.
- Scopes: `openid`, `email`, `aws.cognito.signin.user.admin`. The last scope is needed by existing Cognito account/self-service and online revocation checks; it is not an IAM administrator grant.
- Only Cognito as identity provider. Read email, verified-email status and subject; write email only. User-existence protection and token revocation enabled.
- Five-minute access/ID tokens and authentication challenge session; one-hour refresh token. Refresh rotation is explicitly disabled, matching the existing refresh-auth policy. Tokens remain in memory and are revoked at sign-out. Changing that policy needs corresponding lifecycle tests.
- Keep the existing web client, pool, MFA/signup policy, Canadian region, Lite tier, domain and classic hosted UI. This proposal does not authorize an IAM expansion, pool replacement, paid feature tier or branding upgrade.

## Prepare and inspect

Run from the repository root with Node 22+. Substitute the verified existing pool ID; do not create a second pool.

```powershell
$nativePoolId = 'REPLACE_WITH_EXISTING_CANADIAN_POOL_ID'
$existingWebClientId = 'REPLACE_WITH_EXISTING_WEB_CLIENT_ID'
$nativeProposal = Join-Path $env:TEMP 'qfn-native-client-proposal.json'
node desktop/scripts/native-client-config.cjs generate $nativePoolId | Set-Content -Encoding utf8NoBOM $nativeProposal
if ($LASTEXITCODE -ne 0) { throw 'Configuration generation failed' }
```

Review the generated JSON before any AWS mutation. An authorized operator must first inspect existing clients for `quiz-from-notes-desktop-preview`, avoiding duplicate creation after an uncertain result. Reuse an existing matching dedicated client only after the checks below pass. Never update the working web client to repurpose it.

For a reviewed, confirmed-absent dedicated client, an operator with the existing necessary permissions can create it:

```powershell
aws cognito-idp create-user-pool-client --region ca-central-1 --cli-input-json "file://$nativeProposal" --query 'UserPoolClient.ClientId' --output text
```

Record the returned public client ID. Do not create/upload a client secret. Inspect that specific new client into a temporary local file and run the offline check:

```powershell
$nativeClientId = 'REPLACE_WITH_RETURNED_DESKTOP_CLIENT_ID'
$nativeDescription = Join-Path $env:TEMP 'qfn-native-client-description.json'
aws cognito-idp describe-user-pool-client --region ca-central-1 --user-pool-id $nativePoolId --client-id $nativeClientId --output json | Set-Content -Encoding utf8NoBOM $nativeDescription
if ($LASTEXITCODE -ne 0) { throw 'Client inspection failed' }
node desktop/scripts/native-client-config.cjs verify $nativePoolId $existingWebClientId $nativeDescription
if ($LASTEXITCODE -ne 0) { throw 'Client settings do not match the reviewed proposal' }
```

The verifier checks the exact callbacks/scopes/flows/attributes/lifetimes, a distinct client ID, absence of a secret and unreviewed fields, and no analytics or propagated context. It prints only pass/fail; raw input is bounded and never echoed. This confirms client configuration only, not token acceptance or login availability.

## Activation gates still required

Verify the new client's hosted login actually renders on the existing classic domain. AWS distinguishes classic `SetUICustomization` from the newer managed-login branding API; preserve classic branding and do not upgrade the pool tier to solve a missing login page. Apply only reviewed per-client classic branding if needed, then repeat signed-out navigation checks.

Complete Windows callback handling, the reviewed main-process/renderer boundary and real-account/MFA acceptance before activating. Set the public desktop client ID explicitly in both API and identity service configuration (`COGNITO_DESKTOP_CLIENT_ID`) only as part of a reviewed application deployment, preserving the web client ID. Pin the same pool/client pair in the desktop build; never let a renderer or callback choose an issuer/client. Follow `native-auth.md` for session, sign-out, account isolation and storage requirements. Current deployment controllers have no dedicated native-client provisioning operation; this document does not expand their permissions.

If registration succeeds but later acceptance fails, leave native login disabled and keep the existing web/preview flow. Do not delete the pool or web client. Removing an unused dedicated desktop client is a separately reviewed operator cleanup.
